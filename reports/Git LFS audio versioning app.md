# Lock the Session, Diff the Sound

Build the app as a lock-first, audio-aware layer over plain git and Git LFS. Do not build it as a merge engine. Git LFS is an adequate storage backbone: it replaces each binary with a ~130-byte pointer and can serve bytes from any object store through its batch API. But it **stores every revision of a file whole**, so costs follow the team's workflow (for example, re-rendering 40 stems under the same filenames) far more than its track count. A self-hosted Forgejo server on S3-compatible storage avoids GitHub's **$0.0875/GiB download metering** and its **2 GB per-file cap on Free/Pro**. No DAW project format can be safely auto-merged, and only Reaper, Ardour and Ableton (gzipped XML) are even text-diffable. The right model is therefore exclusive check-out locks on project files, branches presented as "alt versions," and merges that mean "pick one." The diff that works across every DAW is the audio itself: a tiered pipeline that runs from LFS hash to decoded-PCM hash to aligned null test and spectral difference, shown in a loudness-matched A/B player with precomputed waveforms. The market history points the same way. Every hosted project-sync service closed, each ending with a "download your projects now" notice: Splice Studio (2023), Blend and Endlesss (2024), and Ohm Studio. Narrow bounce-review tools and Anchorpoint's artist-friendly git client are still running. The MVP should assemble proven parts: bundled git/git-lfs binaries in a Tauri or Electron shell, Forgejo on object storage, a webhook pipeline keyed by LFS object ID, and a wavesurfer.js or peaks.js review page. Custom merges, real-time co-editing and novel storage formats should wait.

## Git LFS stores every revision whole, so workflow decides the bill

Git LFS works through filters declared in `.gitattributes`. On `git add`, the clean filter hashes the file with SHA-256, moves it into `.git/lfs/objects/OID[0:2]/OID[2:4]/OID`, and commits a small UTF-8 pointer (`version`, `oid sha256:…`, `size`) in its place. On checkout, the smudge filter swaps the real bytes back in. **Uploads happen only at `git push`**, through a pre-push hook ([git-lfs spec](https://github.com/git-lfs/git-lfs/blob/main/docs/spec.md)). Transfers go through a JSON batch API whose per-object `href` and `header` fields can point anywhere. A custom server can therefore answer with presigned S3/R2 URLs, so audio moves directly between laptop and bucket while the app server handles only auth and metadata. If the server already holds an object, the response omits `actions`, which gives free whole-file deduplication ([Batch API](https://github.com/git-lfs/git-lfs/blob/main/docs/api/batch.md)). Two more extension points matter for later phases: custom and standalone transfer agents, which speak line-delimited JSON over stdin/stdout and emit per-object `progress` events ([custom transfers](https://github.com/git-lfs/git-lfs/blob/main/docs/custom-transfers.md)), and resumable tus.io uploads (`lfs.tustransfers=true`) for multi-gigabyte pushes from home studios ([git-lfs-config](https://github.com/git-lfs/git-lfs/blob/main/docs/man/git-lfs-config.adoc)).

The core limitation is that LFS has **no delta or chunk deduplication**. GitHub's billing documentation says that pushing a changed LFS file counts the entire file again ([GitHub Docs](https://docs.github.com/en/billing/concepts/product-billing/git-lfs)). Hugging Face puts it more bluntly: LFS is "designed to notice only that a file has changed and store the entirety of that revision" ([Hugging Face](https://huggingface.co/docs/hub/xet/deduplication)). Clients also hold LFS content twice, once in the object store and once in the working tree ([codenote.net](https://codenote.net/en/posts/github-large-binaries-git-lfs-alternatives/)), so 20 GB of stems needs about 40 GB of disk.

### The arithmetic of a real album

Uncompressed 48 kHz/24-bit stereo audio runs 288,000 bytes per second, or **17.28 MB per minute** (8.64 MB for mono). A 4-minute song with 25 mono and 15 stereo tracks is therefore about **1.9 GB**. Growth then depends on how the team works. Twenty revisions that only touch the project file add about 0.1 GB. Twenty revisions that each add three takes and a mix bounce reach about **5.4 GB**. Twenty rounds of re-rendering all 40 stems under the same filenames, the common pattern when stems pass between studios, reach about **40 GB** for one song. With ten songs, normal production plus three stem-exchange rounds per song, an album lands near **111 GB**. On GitHub Team that fits within included storage. Five collaborators each pulling the album once is about 555 GB of egress, roughly **$27 of overage that month**, and every re-clone or CI run adds more. On Free/Pro the same month costs about $7 in storage plus $48 in bandwidth. On Bitbucket it is about $20 in flat storage blocks with no egress charge found. These calculations use GitHub's published rates ([GitHub Docs](https://docs.github.com/en/billing/concepts/product-billing/git-lfs)). They also show that **bandwidth, not storage, is the line item that scales with team size**.

Independent measurements from the pre-release Wit project support this. In Wit's tests, a localized audio edit cost about 1.1 MB, but a global gain change cost about 16.8 MB, a full second copy: "LFS does not fix that; it just moves the copies elsewhere." Most of Wit's 26 GB → 12 GB saving came from deduplication and FLAC, and only about 0.3 GB came from history ([sep-lab/Wit](https://github.com/sep-lab/Wit)). The design consequence is that write-once take naming, committing bounces and stems only at milestones, and archiving stems as FLAC do more for cost than the choice of backend.

### Fetch only the song you are working on

LFS can limit what each musician pulls. `lfs.fetchinclude`/`fetchexclude` restrict fetches to path patterns. "Recent" windows default to 7 days of refs and 0 days of older commits, and pruning waits 3 extra days (`lfs.pruneoffsetdays`). `lfs.storage` can move the object store onto an external audio drive or a cache shared across projects ([git-lfs-config](https://github.com/git-lfs/git-lfs/blob/main/docs/man/git-lfs-config.adoc)). The app should make the song the unit of hydration: clone metadata only, then pull one song's audio on demand. Skip-smudge clones and sparse checkout are standard techniques but were not re-verified for this report. Long uploads need generous token lifetimes. Gitea raised its LFS auth expiry to 24 hours because multi-gigabyte pushes over slow links were failing ([Forgejo source](https://git.fb1.uni-bremen.de/davrot/forgejo_fusion/src/branch/main/modules/setting/lfs.go)).

### Content-defined chunking is a later lever, not an MVP requirement

The main alternative is content-defined chunking. Hugging Face's Xet (formerly XetHub) splits files into **~64 KB content-defined chunks** grouped into 64 MB blocks and stores only new chunks, while staying backward compatible with LFS pointers ([HF Xet](https://huggingface.co/docs/hub/xet/deduplication); [Xet protocol](https://huggingface.co/docs/xet/index)). The researchers reasoned about how this applies to audio but did not benchmark it. Appending a take or punching in a region would cost only the changed chunks. Gain changes, normalization, sample-rate conversion and lossy re-encodes change every sample and dedupe to roughly nothing under any scheme. Most DAWs record non-destructively, with new takes written as new files, so chunking pays off mainly in destructive and "render-in-place" workflows. git-annex, DVC and git-sfs also store whole files. Diversion, Anchorpoint, Perforce and Unity VCS compete on UX and locking, not on smaller storage ([Anchorpoint](https://www.anchorpoint.app/blog/5-alternatives-to-git-lfs-for-game-development); [Diversion](https://diversion.dev/compare-diversion-to-git-lfs)). A custom transfer agent is where chunking could be added later without changing git semantics. Whether Xet can be self-hosted outside Hugging Face is unverified.

## Audio diffs work as a ladder, from hashes up to listening

No maintained open-source tool runs the whole chain of decode, align, gain-match, null and report changed regions. The researchers found partial projects (sounddiff, smart-audio-diff, audalign, a ComfyUI GCC-PHAT node), but none is a dependable dependency, so the team should expect to write the core itself: roughly 200 lines of numpy/scipy or Rust. The design principle is to **run cheap tests first and stop as soon as one gives an answer**, caching every result by LFS OID, or by the pair (oidA, oidB) for pairwise diffs.

| Tier | Test | Answers | Tooling |
|---|---|---|---|
| 0 | LFS OIDs equal | "Byte-identical" | free from git |
| 1 | Metadata/loudness text dump | "Sample rate, tags, markers, LUFS changed" | ffprobe, BWF MetaEdit, ffmpeg `ebur128`, git textconv |
| 2 | Decoded-PCM hash | "Tags changed, audio identical" or "lossless WAV→FLAC" | ffmpeg `-f hash` with explicit sample format |
| 3 | Per-second chunk hashes | "Seconds 42–57 changed" (lossless only) | ffmpeg `framemd5` or custom |
| 4 | Aligned, gain-matched null test | "−1.5 dB gain", "12 ms offset", residual regions | scipy `correlate` + `correlation_lags` |
| 5 | Spectral/feature difference | "Change at 2–4 kHz" (EQ), "new instrument" | STFT difference, chroma/MFCC |
| 6 | Perceptual / fingerprint | "Transcode degraded quality", "same material re-recorded" | ViSQOL v3, GstPEAQ, Chromaprint |

**Tiers 0–3: metadata and hashes.** The cheapest useful diff is a git `textconv` driver that prints sorted, one-fact-per-line metadata, with `cachetextconv = true`. Git then stores each blob's output in `refs/notes/textconv/<driver>`, so even a slow loudness scan runs once per version, and colors and `--word-diff` work as usual ([gitattributes](https://git-scm.com/docs/gitattributes)). FFmpeg's `ebur128` filter reports integrated LUFS and true peak per BS.1770 ([FFmpeg-cvslog](https://lists.mplayerhq.hu/pipermail/ffmpeg-cvslog/2023-May/137179.html)). BWF MetaEdit exports bext, INFO and, since v21.07, `cue`/`adtl` marker chunks ([FADGI](https://www.digitizationguidelines.gov/audio-visual/documents/help_home.html)). Python's `audiodiff` shows the identity pattern: compare normalized tags plus a SHA-1 of decoded 24-bit PCM, and ignore volatile fields like `encodedby` ([audiodiff](https://audiodiff.readthedocs.io/)). Store a decoded-PCM hash next to each OID so metadata-only edits can be labeled honestly. There is a trap here: FFmpeg's `hash` muxer defaults to `pcm_s16le`, which **silently truncates float or 24-bit sources** and can make different files collide, so always set the codec explicitly ([FFmpeg-devel](https://ffmpeg.org/pipermail/ffmpeg-devel/2022-November/304066.html)). Per-packet `framemd5` hashes locate changed regions in a single linear pass ([FFmpeg wiki](https://fftrac-bg.ffmpeg.org/wiki/framemd5%20Intro%20and%20HowTo)). They are exact only for lossless sources, because lossy decodes are not bit-reproducible across machines ([audiodiff](https://audiodiff.readthedocs.io/)). Whether git hands textconv the smudged audio or the pointer when objects have not been fetched is unverified. The script should detect a pointer and print its OID and size.

**Tier 4: the null test.** Decode both files to float at a common rate. Estimate the offset with FFT cross-correlation, using `scipy.signal.correlate(method="fft")` and `correlation_lags`, which avoids the usual zero-lag indexing bug ([SciPy](https://docs.scipy.org/doc/scipy/reference/generated/scipy.signal.correlation_lags.html)). Then fit gain by least squares, subtract, and report null depth plus windowed residual regions as `[start, end, peak_dB]` for the UI. MP3 needs special care. The LAME tag stores encoder delay and padding, decoders add about 529 samples of their own ([libmp3lame](https://libmp3lame.web.app/article/how-libmp3lame-achieves-gapless-mp3-playback)), and different toolchains decode the same file to different lengths. FFmpeg after `-c copy` gained trailing samples ([trac #9755](https://trac.ffmpeg.org/ticket/9755)), and Audacity 3.2.0 stopped trimming LAME padding ([Audacity forum](https://forum.audacityteam.org/t/3-2-2-mp3-duration-wrong/66369)). So pin one gapless-aware decoder and record which one produced each analysis. Three more reasoned rules apply. A residual near the theoretical floor of the lower bit depth should be reported as a *format* change, not a content change. Polarity flips and L/R swaps should be named as transforms, not shown as full-file diffs. Ripple edits in the middle of a file break global alignment, so align piecewise and fall back to DTW on chroma features.

**Tiers 5–6: perception.** A time-aligned spectrogram difference is the most informative view of a mix revision, because it shows *where in frequency* a change happened. Perceptual metrics answer a narrower question. **ViSQOL v3 in audio mode** (48 kHz, maximum MOS about 4.75) is the practical open full-reference metric ([arXiv 2004.09584](https://arxiv.org/abs/2004.09584); [google/visqol](https://github.com/google/visqol)). GstPEAQ is LGPL but explicitly non-conformant to BS.1387 ([DAFx-15](https://dafx.de/paper-archive/details/cHfHWwcZJB8k3KwAtdoigw)), and its patent position is unverified. PESQ is speech-only. Both ViSQOL and PEAQ assume one file is the "reference," so they suit checks like "did the MP3 preview degrade the WAV master?" and not judgments about creative mix changes. For "is this the same take?", compare Chromaprint `fpcalc -raw` fingerprints by XOR/popcount bit error rate after an offset search. Scores of 0.95 or higher are effectively identical, and clips under 2–3 seconds cannot be fingerprinted ([AcoustID group](https://groups.google.com/g/acoustid/c/mkZ_eQ0vaFQ); [go-fingerprint](https://pkg.go.dev/github.com/go-fingerprint/fingerprint)). No published thresholds map null depth or ViSQOL scores to "audible difference" for music mixes, so the app's labels will need calibrating with listening tests.

**The UI is where this becomes useful to musicians.** Generate multi-resolution peaks with BBC's `audiowaveform`. It is GPL-3.0, so run it as a separate CLI process. It reads MP3, WAV, FLAC and Ogg, but not AIFF ([bbc/audiowaveform](https://github.com/bbc/audiowaveform)). Generate 8-bit `.dat` files for peaks.js, which rejects 16-bit waveform data ([peaks.js](https://github.com/bbc/peaks.js)). Feed wavesurfer.js precomputed `peaks` and `duration` so the browser never decodes a multi-gigabyte file ([wavesurfer.js](https://wavesurfer.xyz/docs/peaks/)), and draw tier-4 regions with its Regions plugin or with peaks.js segments. The A/B player should start both sources on one `AudioContext` clock, apply the measured offset, crossfade 5–20 ms on switch, and **loudness-match using the LUFS difference**, because otherwise "louder sounds better" biases every comparison. waveform-playlist shows the multitrack layout needed for stem review ([naomiaro](https://naomiaro.github.io/waveform-playlist/examples/waveform-data)).

## Three DAW formats diff as text, and none merges safely

DAW project files fall into three tiers by how much the app can see inside them.

| Reaper | `.rpp` plain-text chunk markup; plugin state base64 | rpp, rppxml, rppp, rpp-parser | A: line + semantic |
| Ardour | `.ardour` plain XML | open source | A |
| Ableton Live | `.als` gzipped XML; VST state as hex | dawtool, bravoh-daw, DawVert | A after `gzip -dc` |
| FL Studio | `.flp` undocumented binary events | PyFLP, flpdiff (FL 9–25, MIT, git driver) | B: semantic only |

Sources disagree on FL Studio 25. flpdiff claims a 100% parse rate on 85 projects across FL 9–25, while Wit reports that FL 25 "adds obfuscation" and describes Pro Tools parsing as obfuscated and legally risky ([Wit](https://github.com/sep-lab/Wit)). Treat FL 25 and Pro Tools parsing as fragile.

**DAWproject** (MIT, Bitwig and PreSonus, 2023) is the only formally schematized format. It is a ZIP of `project.xml` and `metadata.xml` with XSDs, covering tracks, clips, automation and embedded plugin states. Bitwig, Studio One, Cubase 14, Cubasis, VST Live and n-Track support it. **Ableton, Logic, Pro Tools and native Reaper do not** ([bitwig/dawproject](https://github.com/bitwig/dawproject); [Bitwig FAQ](https://www.bitwig.com/support/technical_support/system-requirements-62/)). It is lossy, excludes view state, and must usually be exported through the UI. That makes it a useful sidecar "review diff" for the DAWs that support it, but never a merge target.

**Automatic three-way merging is unsafe in every format.** The text formats carry global ID counters and GUIDs, cross-references (sends, automation targets that point at device IDs) and opaque plugin blobs. Two branches that each add a track will generate colliding IDs. A line-clean merge can be valid syntax and still broken in meaning, and DAWs do not necessarily validate on load. This is an inference from the format structures, but the evidence supports it. The researchers found **no production three-way merge driver for any DAW**. cartmedia's ableton-git says only that "some conflicts can be resolved by looking at the diff" ([ableton-git](https://github.com/cartmedia/ableton-git)). An Ableton forum user found git versioning "hasn't proven to be super useful" ([Ableton forum](https://forum.ableton.com/viewtopic.php?p=1807386)), and a BassBuzz forum skeptic saw little gain for mostly-binary projects ([BassBuzz](https://forum.bassbuzz.com/t/daw-in-combination-with-code-repository/10121)). The value these projects did prove is snapshot, history and recovery. dayvonjersen's auto-commit-on-save tool exists because Ableton clears undo history on save ([repo](https://www.github.com/dayvonjersen/ableton-project-version-control-thing)). For human-readable diffs, flpdiff's output (`~ Channel 'Kick' volume 78% → 100%`, with repeated clip edits collapsed) is the model to copy. Plugin blobs should collapse to "plugin X state changed (hash a1b2→c3d4)."

### Locking is the concurrency model, with app UX on top

The Git LFS locking API is a server-side registry keyed by path. `POST /locks` returns 409 if the path is already held. `/locks/verify` runs on push and **halts a push that touches someone else's lock**. Files marked `lockable` stay read-only locally until locked ([Locking API](https://github.com/git-lfs/git-lfs/blob/main/docs/api/locking.md); [File Locking wiki](https://github.com/git-lfs/git-lfs/wiki/File-Locking)). The mechanism has real weaknesses. Servers without the API return 404, and the push proceeds anyway. Locks are advisory and keyed by path, not branch. Few LFS servers implement the API at all, and Giftless has none ([Giftless](https://datahub.io/docs/dms/giftless)). GitHub's web UI ignores locks ([DEV Community](https://dev.to/devactivity/unlocking-productivity-why-githubs-web-ui-must-respect-git-lfs-locks-2afb)), and GitKraken cannot manage them ([GitKraken feedback](https://feedback.gitkraken.com/suggestions/220717/support-git-lfs-large-file-storage-locking-feature)). Anchorpoint, the most mature artist-facing git client, **does not use LFS locks**. It runs its own metadata lock server, auto-locks binaries when they are modified, releases the locks on push, and marks files changed on other active branches as "outdated" ([Anchorpoint docs](https://docs.anchorpoint.app/git/file-locking/)). It also documents that write protection fails on NAS mounts and that some tools ignore read-only flags. There are DAW-specific problems as well. Logic's `.logicx` is a directory bundle, so locking one file inside it protects nothing else, and read-only flags can break autosave and backup writes inside project folders. Whether each DAW handles a read-only project file gracefully is **untested and must be checked empirically** before launch.

The recommended strategy is lock-first. Mark only project files lockable, plus folders where audio is edited destructively in place. Recorded takes are write-once with unique names, and making every WAV read-only would gain nothing and risk breaking DAW writes. The app acquires the lock automatically on first modification, or when it detects the DAW opening the project. It sets `lfs.locksverify=true` so lock errors block pushes instead of producing warnings, and it releases locks after a successful publish. When a conflict happens anyway, after offline work or a forced unlock, the app never merges. It keeps the remote file as the canonical version, saves the local one as `Song (Alex's conflict copy 2026-11-19).als`, and opens a comment thread for the producer to resolve.

### Portability needs a lint, not a hope

Every DAW saves *references* to media by default. Ableton's Collect All and Save copies audio into `Samples/Collected`, but **plugins cannot be collected**, some Max for Live devices break after collecting, and deleting `Ableton Project Info` causes "missing media" errors ([Ableton help](https://help.ableton.com/hc/en-us/articles/209775645); [Max for Live](https://help.ableton.com/hc/en-us/articles/209069749-Max-for-Live-devices-stop-working-after-Collect-All-and-Save)). Ableton's `FileRef` stores relative and absolute paths plus `OriginalFileSize`/`OriginalCrc`, which a pre-commit lint can check for paths that leave the repo ([ableton-under-the-hood](https://github.com/Sample-Offline/ableton-under-the-hood)). Commercial libraries and plugins should stay out of repos. In their place, generate a per-commit manifest of plugins (name, vendor, format, version) and sample hashes with a bravoh-daw-style parser, and warn "Missing: FabFilter Pro-Q 4" before the project opens. Soundtrap's October 2026 feature, which lets collaborators hear third-party effects without owning them, shows that plugin mismatch is a recognized blocker ([Bedroom Producers Blog](https://bedroomproducersblog.com/2026/10/12/soundtrap-third-party-plugins/)). A starter `.gitattributes` that reconciles the notes is below. Two choices in it go against one of the draft templates: audio is not lockable by default, and `Ableton Project Info/` is kept, not ignored, because of Ableton's warning.

```gitattributes
*.wav   filter=lfs diff=audio merge=lfs -text
*.aif   filter=lfs diff=audio merge=lfs -text
*.aiff  filter=lfs diff=audio merge=lfs -text
*.flac  filter=lfs diff=audio merge=lfs -text
*.mp3   filter=lfs diff=audio merge=lfs -text
Audio/Edits/** lockable
Masters/**     lockable
*.als   filter=lfs diff=als   merge=binary -text lockable
*.flp   filter=lfs diff=flp   merge=binary -text lockable
*.song  filter=lfs diff=zipxml merge=binary -text lockable
*.ptx   filter=lfs -diff merge=binary -text lockable
*.cpr   filter=lfs -diff merge=binary -text lockable
**/*.logicx/** filter=lfs -diff merge=binary -text
**/*.logicx/Alternatives/*/ProjectData lockable
*.rpp     diff merge=binary lockable
*.ardour  diff merge=binary lockable
```

Here `diff.als.textconv` is `gzip -dc`, `zipxml` dumps sorted ZIP entries, and `flp` uses flpdiff's `git-setup` driver ([flpdiff](https://github.com/dawhubapp/flpdiff)). Store `.als` compressed rather than through a gunzip clean filter: a bad smudge produces a project Ableton refuses to open ([ableton-under-the-hood](https://github.com/Sample-Offline/ableton-under-the-hood)). The `.gitignore` should cover Ableton `Backup/`, Pro Tools `Session File Backups/` and `WaveCache.wfm` ([Avid](https://apps.avid.com/proToolsFirstHelp/version12.0/enu/Pro%20Tools%20First%20Help/sess6.Workspace.16.065.html)), Reaper `.RPP-PROX` ([Sound On Sound](https://www.soundonsound.com/techniques/reaper-subprojects)), and Ardour `.bak`, `.pending`, `peaks/` and `analysis/` ([Ardour](https://manual.ardour.org/working-with-sessions/whats-in-a-session)). Patterns for Logic autosaves, FL backups, Studio One history and Cubase caches came from the researchers' general knowledge and need verifying per DAW version.

## Every hosted project-sync service died; narrow tools survived

| Product | Model | Outcome | Stated reason |
|---|---|---|---|
| Splice Studio | Cloud backup and versioning for Ableton, Logic, FL, GarageBand, Studio One | **Discontinued 2023.** Uploads frozen by 10 Mar, no new projects from 7 Apr, sync stopped 31 May (Splice's blog gives 5 Jun as the final date) | "Hasn't been a focus for us since 2017"; users "have many great alternatives for file sharing" |
| Blend.io | Ableton-first collaboration, 13 DAWs; acquired by ROLI 2015 | Shut down June 2024 | None given |
| Endlesss | Collaborative loop jamming | Ceased operations 31 May 2024 | — (CDM notes it "really did connect with people") |
| Ohm Studio | Real-time collaborative DAW | Defunct (2020; shutdown dates conflict) | "Never met a demand strong enough to be commercially sustainable" |
| Avid Pro Tools First / cloud | Free tier tied to cloud collaboration | Discontinued Dec 2021; old free-cloud projects cleared | Infrastructure reportedly expensive to maintain |

Sources: [MusicRadar](https://musicradar.com/news/splice-studio-closing), [Splice blog](https://splice.com/blog/announcing-splice-studio-v2/), [TechCrunch](https://techcrunch.com/2015/10/23/roli-makers-of-the-new-seaboard-rise-acquire-betaworks-backed-blend-io), [CDM](https://cdm.link/2024/05/endlesss-discontinued/), [MusicTech](https://musictech.com/news/gear/tim-exile-endlesss-app-shut-down/), [Ohm Studio](https://www.ohmstudio.com/), [Production Expert](https://www.production-expert.com/home-page/pro-tools-first-discontinued-what-does-this-mean?format=amp). One research note cited 2026 marketing pages describing a current Splice snapshot feature. That conflicts with Splice's own shutdown announcement and the dated phase-out coverage, so Splice Studio is treated as discontinued. Avid's Cloud Collaboration product page still exists but is undated, and its current status is unclear ([Avid](https://cn.avid.com/pro-tools/cloud-collaboration)).

The pattern is structural. Services that stored and synced full multi-DAW projects on their own servers carried heavy infrastructure costs and competed with file sync, which users treat as a commodity. Each ended by telling users to download their work before a deadline. The survivors are narrow and cheap to run. Pibox handles bounce review and approvals inside the Pro Tools side panel, with every new bounce landing under the same link as a new version ([Pibox](https://pibox.com/)). Notetracks offers timestamped comments ([Notetracks](https://www.notetracks.com/)), and Feedtracks sells version stacks with notes ([Feedtracks](https://feedtracks.com/blog/version-control-nightmare-how-producers-can-stop-losing-final-mixes)). Audiomovers streams audio from the DAW to a browser and charges the sender while listeners use it free. BandLab and Soundtrap survive because they version only inside their own DAWs. CDM raises a fair objection: online collaboration "really *can't* be provided without a service," and the hard problem is attaching that service to a sustainable production-tools business ([CDM](https://cdm.link/2024/05/endlesss-discontinued/)). A git-based design answers both sides of that. The service sells locks, review links, processing and optional hosting. The team's work always lives in a plain git repo on storage it controls, so a vendor shutdown cannot strand it.

The closest analogue comes from game development. **Anchorpoint** is a git + LFS desktop client for artists. It auto-writes `.gitattributes`, runs its own lock server, shows previews in history, supports selective checkout and local pruning, and costs €20–25 per user per month ([Anchorpoint](https://www.anchorpoint.app/policies/facts); [Git for artists](https://www.anchorpoint.app/features/git-for-artists)). Its own framing describes the gap this app fills: LFS "solves the storage problem" but "doesn't address the 'human' problem" ([Anchorpoint blog](https://www.anchorpoint.app/blog/version-control-for-binary-files)). Anchorpoint claims to "understand" audio formats, but no audio diff or A/B features were found. Diversion (100 GB free, then $10 per 100 GB, with vendor pages inconsistent on seat prices), Unity VCS's Gluon and Perforce all compete with centralized exclusive checkout, which artists rely on ([Diversion](https://www.diversion.dev/pricing); [Assembla](https://get.assembla.com/blog/perforce-vs-plasticscm-indie-game-dev-teams/)). Mainstream git GUIs are a poor fit: GitHub Desktop requires LFS to be set up from the command line ([GitHub Docs](https://docs.github.com/en/enterprise-cloud@latest/desktop/configuring-and-customizing-github-desktop/about-git-large-file-storage-and-github-desktop)). In music, the direct competitor is **dawhub.app**, a hosted FL Studio collaboration product built on flpdiff. A wave of small 2025–2026 "git for music" projects (StemHub, Wit, kit-vcs, gitcrusher, GitDaw) confirms the demand, but none has shipped at scale ([StemHub](https://github.com/stemhub-org/Stemhub); [Wit](https://github.com/sep-lab/Wit)). The researchers found no usable Reddit or survey data, but the anecdotal pain points are consistent: "Final_Mix_v3_REAL_FINAL_MASTER.wav" naming, not knowing which version the client approved, stem handoff to mastering, and portability between machines ([Feedtracks](https://feedtracks.com/blog/version-control-nightmare-how-producers-can-stop-losing-final-mixes); [Gearspace](https://gearspace.com/threads/reinforcing-mix-elements-with-stems.1452024/page-2#post-17518184)). The app can differentiate on three things together: multi-DAW support, audio-native diff and review, and data the team owns.

## Bundle the git CLI, host on Forgejo, key everything by object ID

### Desktop client

Production git apps bundle the real `git` and `git-lfs` binaries and shell out to them, because **libgit2 has no LFS** ([NixOS PR](https://github.meowingcats01.workers.dev/NixOS/nix/pull/8186)) and gitoxide's LFS crate is at 0% ([docs.rs](https://docs.rs/crate/git-lfs/0.0.0)). GitHub Desktop is built on dugite, which ships a portable Git with Git LFS and Git Credential Manager included ([dugite-native](https://github.com/desktop/dugite-native)). Tauri v2 bundles the same binaries as `externalBin` sidecars with allowlisted arguments ([Tauri](https://v2.tauri.app/develop/sidecar/)), and GitButler shows that Tauri plus Rust works for a production git client ([GitButler](https://github.com/Byron/gitbutler)). The recommended stack is Tauri v2 with git and git-lfs sidecars. gitoxide or git2 can serve fast read-only paths such as status, log and text diffs of `.rpp`. Every network and LFS operation goes through the CLI, and lock dashboards and progress bars call the `/locks` and batch endpoints directly over HTTP. Electron plus dugite is the lower-risk choice for a JavaScript-heavy team. Authentication should use OAuth or a token handed to git through a custom credential helper, with SSH as an advanced option. The file watcher has to treat temp-write-then-rename as a save, because a modify-only watcher misses atomic saves ([Eclectic Light](https://eclecticlight.co/2020/04/17/how-apps-save-changed-files/)). It should debounce until size and modification time stop changing. It must never snapshot mid-recording: Ableton keeps new takes in a temp folder until save ([Ableton](https://help.ableton.com/hc/en-us/articles/5809449695900)). Before any checkout, the app should check for open file handles (lsof on macOS, Restart Manager on Windows) and ask the user to close the session in the DAW first.

### Server and processing pipeline

Forgejo provides git hosting, LFS, lock settings and webhooks in one binary. Its `[lfs]` storage section points at any S3-compatible store (MinIO, R2, Garage) ([Forgejo storage](https://forgejo.org/docs/v8.0/admin/storage)). Lock support appears in Forgejo's source settings ([lfs.go](https://git.fb1.uni-bremen.de/davrot/forgejo_backup/src/commit/ff18c3ba65b230f30c07e99277730a217576ee99/modules/setting/lfs.go)), but the endpoints were not verified, so test them in the first week. A small API service with Postgres sits beside Forgejo. It owns users, roles, comments, approvals and lock presence, and it consumes push webhooks. A standalone LFS server is optional. rudolfs adds XChaCha20 at-rest encryption and a disk cache that cuts S3 egress, but **losing or changing its key makes every object unreadable** ([rudolfs](https://docs.rs/crate/rudolfs/0.3.6/source/README.md)). Giftless offers pluggable backends but no locking ([Giftless](https://giftless.readthedocs.io/en/v0.5.0/storage-backends.html)).

```
DAW ──saves──▶ Desktop app (Tauri + git/git-lfs sidecars, watcher, lock UX)
                 │  git push (pointers)        │  LFS batch → presigned PUT
                 ▼                             ▼
            Forgejo (git, LFS API, locks) ──▶ S3-compatible bucket (OID-keyed)
                 │ push webhook                ▲ stream by OID
                 ▼                             │
            API + Postgres queue ──▶ Workers: audiowaveform, ffmpeg preview,
            (roles, comments,               ebur128 LUFS, spectrogram, PCM hash,
             approvals, GC refs)            pairwise null-diff (oidA,oidB)
                 │
                 ▼
            Web review (wavesurfer.js/peaks.js, A/B, timestamped comments,
            "Approve" → protected tag approved/mix-v3; guest links, no git)
```

The worker runs `git diff-tree` on each push, reads the pointer files of changed audio, and enqueues jobs for each OID it has not seen. Because the OID is the content's SHA-256 ([rudolfs](https://docs.rs/crate/rudolfs/0.3.6/source/README.md)), every derived artifact is computed once and shared across branches, versions and repos. Store each one at `derived/{oid}/{kind}-{paramsVersion}`. A Postgres-backed queue (pg-boss, River, graphile-worker) avoids extra infrastructure at MVP scale. Garbage collection is a known weak spot. GitLab's orphan-LFS rake task **does not clean object storage** ([GitLab #391317](https://gitlab.com/gitlab-org/gitlab/-/issues/391317)), so build reference counting from the webhook scans, with a 30-day grace period. Move objects referenced only by old, untagged commits to cold storage, and keep approved masters on hot storage. Presigned preview URLs should be scoped separately from stem downloads, so a client on a review link never gets raw multitracks.

### Team workflow in studio language

The interface should never show git verbs. A commit is "Save version," with a required note. Push becomes part of "Publish": commit, pull, push, release locks. Fetch is "What's new," a branch is an "Alt version," merge is "Make this the main version" (always pick one, never a content merge), a tag is a "Milestone" or "Approved," and a lock reads "Checked out by Alex." Anchorpoint likewise describes a commit as "a checkpoint for your project" ([Anchorpoint](https://www.anchorpoint.app/blog/version-control-for-binary-files)). Branching should be trunk-based. `main` is the song. Alt ideas live on short branches with cross-branch "outdated" warnings. Mix revisions are tags on `main`, not branches. The producer can approve, tag and force-unlock. Engineers can write and lock. Artists write only in their own recording folders and can comment. Clients and labels get review-only web links. Protected `approved/*` tags enforce the approval step.

Each song gets one repo, with a fixed layout: `Project/` (lockable), `Audio/Recordings/` (write-once takes), `Audio/Edits/`, `Stems/v{N}/`, `Bounces/`, `Masters/`, and `Docs/` holding lyrics and `plugins.json`. Stems all start at 0:00, share one sample rate and bit depth, and state in their names whether effects are printed. Shared team sample packs live in a separate repo cloned to a fixed path, not as submodules, which confuse non-technical users and break DAW paths. This layout puts the rules that limit storage growth (write-once takes, milestone-only stems) into the folder structure itself, so the team does not have to remember them.

## Ship proven parts first and research problems last

| Phase | Scope | Why it is safe |
|---|---|---|
| 0: Validation (≈4–6 weeks) | Test each target DAW's behavior with read-only project files, atomic saves and open-handle locks. Confirm Forgejo lock endpoints and `lfs.locksverify` blocking. Confirm textconv receives smudged audio. Interview 5–10 studios about revision habits | Removes the unverified assumptions the design depends on |
| 1: MVP (≈3–4 months, a judgment estimate) | Tauri app with bundled git/LFS. Project create/join with templated `.gitattributes`/`.gitignore`. Watcher and "Save version." Publish/Get latest. History with Listen/Restore. Auto-lock on modify, release on push, producer force-unlock, conflict copies. Forgejo + R2/MinIO. API + Postgres queue running peaks, preview, LUFS and PCM hash per OID. Web player with timestamped comments and "Approve" tags. Per-song selective fetch | Every component has a shipping precedent (dugite, Anchorpoint, peaks.js, Forgejo) |
| 2: Review depth | Loudness-matched, aligned A/B. Null-test regions and spectrogram diff. Guest review links. Alt versions with outdated warnings. Plugin/sample manifests (Ableton, Reaper, FL first). Portability lint. Semantic diffs for `.rpp`, `.als`, `.flp`. Notifications | Builds on the OID cache and existing parsers |
| 3: Studio scale | In-DAW actions via Reaper ReaScript and Ableton Remote Scripts. DAWproject sidecar diffs. Sample resolution by hash. Storage tiering and refcount GC. Customer-managed encryption. Optional dedicated lock service | Needs Phase 1–2 usage data to prioritize |
| Deferred | Real-time co-editing, audio or project content merges, custom chunked storage (Xet-style) | No precedent, high cost, unproven demand |

The roadmap's order follows the evidence. Snapshot, recovery, locking and bounce review have demonstrated value. Merges and real-time collaboration either have no working precedent or killed the companies that hosted them. A content-defined-chunking transfer agent belongs in Phase 3 or later, and only if telemetry shows stem-exchange re-renders dominating storage. No published benchmark yet shows how chunking performs on real studio audio.

## Conclusion

The research shifts the design goal. The hard problem is not "git for audio"; Git LFS already stores audio adequately, and its costs can be predicted from a team's workflow. The hard problem is that DAW sessions are single-writer documents that cannot be merged and that git's optimistic model ignores. A lock-first app that treats branches as alternatives and merges as choices therefore fits musicians better than any attempt at semantic merging. The audio is the one diff surface that works across every DAW, which makes null tests, spectral differences and loudness-matched A/B the product's core feature, not an extra. Parsing Logic, Pro Tools and Cubase files can stay a stretch goal.

The failed products also suggest a business model. Splice Studio, Blend, Endlesss and Ohm Studio did not fail for lack of users. They failed because they owned expensive storage that users saw as a commodity. An app that leaves the team's history in a portable git repo, and charges per seat for locks, review, analysis and optional hosting, avoids that trap and makes data ownership a selling point. The biggest remaining risks are not technical. No one has studied how musicians actually work with git, and per-DAW behavior with read-only files and atomic saves is still untested. Both questions are cheap to answer in a validation phase, so they belong before the first line of product code.
